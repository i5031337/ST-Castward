# Gemma 4 E4B natural-prose tracker evaluation

On 2026-10-18, the local Gemma 4 E4B reader handled **96/98 audited checks (97.96%)** across sixteen trials: eight two-paragraph Fantasy Adventure and Dating Sim scenes, each run twice. The latest story messages supplied no explicit stat amounts. Both sound-sleep trials restored Social Energy from `2/10` to `10/10`. In both shared-recovery trials, Alex and Mira each reached `12/12` HP. In both partial-healing trials, Alex and Mira gained HP but remained below their maxima: `3/12 → 4/12` and `4/12 → 5/12` in one run, `3/12 → 5/12` and `4/12 → 6/12` in the other. The two failed checks came from **one reply awarding unearned XP to both Alex and Mira**. This misses the benchmark's zero-critical-failure criterion; the result is promising, not a clean pass.

The [audited prompt bundle](gemma-e4b-natural-prose-generic-partial-npc-audit-prompts.json) and [audited results](gemma-e4b-natural-prose-generic-partial-npc-audit-results.json) retain every raw response, normalized update, applied state, and scored check. The saved request messages match the original frozen bundle byte for byte. An unchanged absolute HP reading and a positive HP delta appeared together in one partial-healing response. We fixed the production normalizer to ignore the unchanged duplicate, then replayed all saved responses consistently. After noticing XP awarded to Mira as well as Alex, we added the NPC XP checks and rescored the same raw responses. Those extra checks are a **post-run audit**, not preregistered independent validation. The runner sends the shipped prompt and System to the local llama.cpp model at port 9931 using server sampling defaults. It uses production parser, stat rules, progression, collection application, and place-review code, with controlled in-memory states. It does not test full SillyTavern conversation continuity, review clicks, or provider scheduling. These stochastic trials cannot establish reliability across arbitrary prose, Systems, or endpoints.

A one-pass regression of the original twelve tracker scenarios with the generalized-pool prompt scored 70/72. It retained the earned-XP battle result. One miss was a present NPC, and one was an opening-place current marker. The opening scene had no depleted recovery pool, so the new hint was absent in that prompt. This stochastic run also misses the original tracker suite's zero-critical-failure criterion.

The first natural-prose trial exposed an under-recovery: the model estimated `+4` and `+2` for a full night. Castward first added an energy-specific hint, then generalized it to all configured numeric pools with live current/maximum readings for the player and present NPCs. XP and Level are excluded. The hint says that complete recovery can fill applicable pools, while partial recovery should give a smaller gain; configured System rules and story limits take precedence. A more guided version of the first six stories passed 66/66 checks, but ordinary narration exposed occasional false XP and other stochastic misses. The review step remains useful.

We also corrected two benchmark mistakes without altering saved model responses. Walking into the named tavern's cellar can legitimately make the cellar the current subplace. A torn sleeve can legitimately update clothing, and Mira's linen can be consumed while treating a wound. The final checks reject unsupported item gains or player inventory changes in those scenes while allowing those evidenced effects. Intermediate runs remain available in Git history; no failed response was replaced.

To repeat with the same local model and running server:

```bash
node tests/eval-gemma-tracker.js --freeze another-natural-run --natural
node tests/eval-gemma-tracker.js --run another-natural-run --repeats 2
```
